01 Component Specifications
Workflow Orchestrator
JavaScript engine — not an LLM. Executes deterministic control flow: spawns agents, enforces concurrency limits (≤10 parallel agents), collects typed outputs, routes data between phases, and handles failures. The key distinction: the orchestrator has no language understanding — it manipulates structured data returned by agents via JSON schemas.
LLM Agent (subagent)
A fresh Claude instance spawned for a single, scoped task. Each agent has no memory of other agents — it receives only its specific input via prompt and returns only its specific output via a structured schema. 30 agents total ran in this session. They are ephemeral: they exist only for the duration of their task.
WebSearch Tool
Queries a search engine index. Returns ranked results with URL, title, and snippet. Works through the session proxy. Snippets are 150–400 character index-generated previews — not the source page content. This is what you see under a Google search result. This tool worked correctly.
WebFetch Tool
Loads the full content of a URL — equivalent to opening a webpage. Should return the complete article or report text for downstream extraction. Failed for all 24 attempts in this session due to proxy configuration blocking outbound fetch requests. The failure is deterministic: same proxy blocks all fetches equally.
Structured Output (JSON Schema)
Each agent is bound to a JSON schema for its return value. The LLM is forced to call a StructuredOutput tool that validates against the schema — it cannot return free text. This means the orchestrator receives typed, programmatically processable data rather than natural language, enabling reliable handoff between pipeline stages.
Journal File
A JSONL file written during workflow execution — one line per completed agent with its full return value. This is what allowed recovery: after the workflow returned empty results, I read the journal directly and extracted the search snippets that the automated pipeline had discarded when fetches failed. The journal is the observable state of the system.
02 Interface Definitions — Data Contracts Between Stages

Each stage hands off a typed schema to the next. The orchestrator treats these as contracts — it does not interpret the content, only routes the structured fields.

P1 → P2: Search Angles Schema
{ "angles": [ { "id": 1, "angle": "string", "search_queries": ["string"] }, ...×5 ] }
Scope agent output. Each angle becomes one search agent's input. 5 angles = 5 parallel agents. The decomposition into independent angles is what enables parallelism — each agent is self-contained with no dependency on others.
P2 → P3: Search Results Schema
{ "results": [ { "url": "string", "title": "string", "snippet": "string (150-400 chars)", "relevance": "high|medium|low" }, ... ] }
Per-agent output from search. Orchestrator collects all 5 result arrays, deduplicates by URL, applies token budget cap, and creates one fetch task per surviving URL. The snippet field is the only content available when fetch fails — it is index-generated metadata, not source text.
P3 → P4: Fetched Content Schema (intended — never populated)
{ "url": "string", "content": "string (full page text)", "claims": [ { "claim": "string", "source_passage": "string", "falsifiable": true } ] }
This schema never received real data. Full page text would feed claim extraction, which would then feed the verification stage. Zero instances completed.
P4 → P5: Verification Results Schema (intended — never populated)
{ "claim": "string", "votes": [ { "verdict": "refuted|confirmed", "reasoning": "string" }, ...×3 ], "survives": boolean }
Three independent adversarial agents vote per claim. Survives = true only if < 2 out of 3 refute. This is the quality gate that was bypassed.
03 Design Decisions — What Was Built and Why

Two layers of decisions exist: those embedded in the pre-built deep-research workflow (architectural defaults), and those I made when invoking it on your prompt.

Decision Who made it Rationale
5 search angles, not 1 Workflow default A single query misses orthogonal aspects of a broad topic. 5 independent angles with no shared phrasing maximize the probability of discovering diverse, non-overlapping sources. Cost: 5× search agent overhead. Benefit: coverage that a single search cannot achieve.
Parallel search (not sequential) Workflow default The 5 search agents have no dependency on each other's outputs. Running them sequentially would increase wall-clock time by 5× with no quality benefit. Parallelism is valid whenever tasks are independent — this is the defining condition.
One fetch agent per URL Workflow default Fetch operations are I/O-bound, not compute-bound. Assigning one agent per URL means slow URLs don't block fast ones. Failure isolation: one failed fetch does not affect others. Contrast with: one agent fetching all 24 URLs sequentially, where a single blocked URL stalls everything.
Adversarial (refute) verify, not confirmatory Workflow default Confirmation bias: if you ask agents "is this claim true?", they will tend to confirm it. Asking agents to actively try to falsify a claim is a deliberate inversion. A claim that survives three dedicated refutation attempts has earned higher confidence than one that passed three confirmation checks. Classic red-team pattern.
3 votes per claim, 2/3 to kill Workflow default Odd number eliminates ties. 3 is the minimum meaningful ensemble — enough diversity without excessive cost. 2/3 threshold is asymmetric toward survival: a claim needs two independent refuters to die. This calibration accepts some false positives (weak claims that survive) in exchange for not killing strong claims based on a single contrarian agent.
Single synthesis agent (not distributed) Workflow default Coherence. Multiple synthesis agents produce fragmented, inconsistent style and structure. The synthesis agent has full context of all surviving claims and can reason about what to merge, what to foreground, and how to structure the output as a whole. The one place sequential execution is the right choice.
Invoking deep-research (not a simpler approach) My decision Your question was broad and explicitly asked for multi-source coverage from named institutions. A single WebSearch or a simple research agent would have returned shallower results. The deep-research workflow is designed exactly for this: structured multi-source synthesis with verification. The failure was environmental, not a workflow mis-selection.
Detailed structured args string My decision The args string I wrote was deliberately structured — naming source preferences (NVIDIA, Stanford HAI, etc.), enumerating the four coverage domains, and specifying the output format ("structured as a taxonomy a practitioner could use to decide where to specialize"). This shapes what the scope agent decomposes into angles. A vague brief produces vague angles and worse coverage.
Read journal, synthesize manually (not re-run) My decision Re-running the workflow would have hit the same proxy failure — the root cause is environmental, not stochastic. Inspecting the journal revealed that 29 search snippets were substantive enough to build the taxonomy structure. Manual synthesis from available evidence was the correct recovery path. Re-running would have wasted 7 minutes and returned the same empty result.
04 Architectural Principles at Work
Specialization enables parallelism. Every agent in this system has exactly one job. That constraint is not accidental — it is what makes parallel execution safe. When each agent is fully self-contained (input → task → output), many can run concurrently without shared state conflicts. The moment an agent needs to know what another agent is doing, it becomes a dependency and must wait.
The orchestrator is not intelligent — by design. The workflow engine that coordinates all agents is a deterministic program, not an LLM. It does not interpret results, does not make judgment calls, and does not hallucinate. All intelligence is encapsulated in the agents it spawns. This separation keeps the control flow reliable and auditable. An LLM orchestrator would introduce non-determinism into the coordination layer.
Structured schemas are the interfaces. Agents do not communicate in natural language — they communicate in typed JSON that the orchestrator can process programmatically. This is what makes the pipeline composable: each stage's output is another stage's input, and the contract between them is explicit. When a schema is violated, the system errors rather than silently propagating garbage.
The failure was systemic, not probabilistic. WebFetch being blocked by the proxy is a configuration fact, not a flaky network condition. All 24 attempts failing identically is the signature of a deterministic block, not random errors. This distinction matters for recovery: re-running solves random failures; fixing the proxy configuration solves deterministic ones. Journal inspection confirmed this immediately — all 24 results had the same "unreliable" marker.
05 What a Complete Run Looks Like

For perspective: in a session with unrestricted WebFetch, the same workflow would have spawned approximately:

1 scope agent + 5 search agents + 15 fetch agents + 3 × N verification agents (where N = number of extracted claims, typically 20–60 for a broad research question) + 1 synthesis agent.

That's roughly 75–100 subagents for a fully executed deep-research run on a question this size, with wall-clock time dominated by the slowest verification batch (not the total agent count, because most run in parallel).

What ran in this session: 30 agents — scope, 5 search, 24 fetch attempts. Verification and final synthesis were entirely absent from the automated pipeline.
