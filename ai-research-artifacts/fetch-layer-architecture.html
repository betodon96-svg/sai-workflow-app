Fetch Layer
Alternative Configurations

The fetch phase of the deep-research pipeline fails in this cloud environment due to an egress policy that blocks outbound HTTPS. This document enumerates five architectural alternatives for a production-grade, background-capable fetch layer.

Root Cause Egress policy — not a tool or code problem
The Claude Code cloud environment routes all outbound HTTPS through a policy-enforcing proxy at 127.0.0.1:38045. Every CONNECT tunnel to an external domain returns 403 policy denial — confirmed across 13 domains including Stanford HAI, arXiv, NVIDIA, McKinsey, and Gartner. This applies uniformly to curl, WebFetch, Python requests, wget, and any HTTP client in the environment. WebSearch works because it routes through an internal Anthropic search API, not a direct CONNECT. The constraint is at the network layer — it cannot be fixed by iterating on fetch code inside the same environment. Each alternative below relocates the fetch operation to a context where the restriction does not apply.
Option A Dedicated Fetch MCP Service
MCP Microservice
Deploy a fetch service, register it as an MCP connector
A small API that fetches, cleans, and returns page text — callable from any workflow as a native tool
Best for production

Deploy a lightweight service (FastAPI, Express, or equivalent) on any unrestricted compute — a VPS, Railway, Fly.io, AWS Lambda. The service exposes one endpoint: given a URL, it fetches the page, extracts clean text (HTML cleaning via BeautifulSoup, PDF text via pdfplumber), and returns structured output the workflow can process directly.

Register it as a custom MCP server in claude.ai connector settings. From that point it appears as a native tool — mcp__fetch__fetch_url — callable in workflow scripts exactly like WebSearch. The workflow does not know or care that the fetch is happening externally; the interface is identical.

This is the cleanest long-term architecture because the fetch capability becomes reusable across all workflows, not just deep-research. It can be extended: caching layer, rate limiting, paywall handling, PDF OCR, screenshot rendering for JS-heavy pages.

Infrastructure
Any always-on compute with open egress — Railway, Fly.io, Render (free tier), AWS Lambda, VPS. ~$0–$7/month at this scale.
Setup effort
~2–3 hours: deploy service, write MCP manifest, register connector in claude.ai settings.
Autonomy
Fully autonomous — no user action required once deployed. Background workflows call it transparently.
PDF support
Yes — pdfplumber or PyMuPDF extracts structured text from PDFs. Can handle the Stanford AI Index and similar reports natively.
Dependency
External service uptime; rate limiting by target sites. Mitigated by caching and retry logic in the service.
Modified pipeline
Search agents → URL list → mcp__fetch__fetch_url ×N (parallel) → Claim extraction → Adversarial verify → Synthesize
# fetch_service.py — minimal FastAPI implementation from fastapi import FastAPI import httpx, pdfplumber, io from bs4 import BeautifulSoup app = FastAPI() @app.post("/fetch") async def fetch_url(url: str): async with httpx.AsyncClient(follow_redirects=True, timeout=30) as client: r = await client.get(url, headers={"User-Agent": "ResearchBot/1.0"}) if "pdf" in r.headers.get("content-type", ""): with pdfplumber.open(io.BytesIO(r.content)) as pdf: text = "\n".join(p.extract_text() or "" for p in pdf.pages[:40]) else: soup = BeautifulSoup(r.text, "html.parser") for tag in soup(["script","style","nav","footer"]): tag.decompose() text = soup.get_text(separator="\n", strip=True) return {"url": url, "title": soup.title.string if soup.title else "", "content": text[:50000], "chars": len(text)}
Option B GitHub Actions as Fetch Runner
GitHub Actions
Trigger a GitHub Action from the workflow — it fetches and commits content back
Uses infrastructure already in place; GitHub Actions runners have unrestricted egress
Best for current stack

GitHub Actions runners have full outbound internet access with no proxy restriction. The deep-research workflow can trigger an action via mcp__github__actions_run_trigger (already in the available toolset), passing a URL list as input. The action fetches all URLs, extracts text, and commits the content to the repo. The workflow then polls mcp__github__actions_get until the action completes, reads the committed files, and continues with claim extraction.

This uses zero new infrastructure — everything is on GitHub, which is already connected. It fits the CLAUDE.md / cowork pattern naturally: the repo becomes the shared state between the workflow and the action runner. Fetched content is also stored persistently, enabling incremental research (don't re-fetch sources already in the corpus).

The one limitation is latency: action startup adds ~30–60 seconds. For a background research workflow this is negligible — the fetch phase already takes 2–5 minutes at scale.

Infrastructure
GitHub Actions — already in use. Free tier: 2,000 min/month (Ubuntu). No new service to deploy.
Setup effort
~1 hour: write the fetch workflow YAML + Python script, commit to repo.
Autonomy
Fully autonomous once set up. Workflow triggers action, polls for completion, reads output — no user touch required.
PDF support
Yes — install pdfplumber in the action, handle PDFs natively.
Bonus
Fetched content accumulates in the repo as a research corpus. Future runs skip already-fetched sources.
Modified pipeline
Search → URL list → Commit URL list to repo (MCP) → Trigger GH Action (actions_run_trigger) → Poll until complete (actions_get) → Read fetched files from repo → Claim extraction → Verify → Synthesize
# .github/workflows/fetch-research-urls.yml name: Research Fetch on: workflow_dispatch: inputs: url_list: description: 'JSON array of URLs to fetch' required: true output_dir: description: 'Repo path to write fetched content' default: 'research-corpus' jobs: fetch: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: pip install requests beautifulsoup4 pdfplumber -q - name: Fetch URLs run: | python scripts/fetch_urls.py \ --urls '${{ inputs.url_list }}' \ --output '${{ inputs.output_dir }}' - name: Commit corpus run: | git config user.name "github-actions" git config user.email "actions@github.com" git add ${{ inputs.output_dir }}/ git diff --cached --quiet || git commit -m "Add fetched research content [skip ci]" git push
Option C Third-Party Fetch API via MCP
External API
Register a web-to-text service as an MCP connector
Jina Reader, Firecrawl, or similar — zero infrastructure to maintain
Good option

Services like Jina.ai Reader (r.jina.ai/[URL]) and Firecrawl convert any URL to clean LLM-ready text via API. If registered as an MCP tool in claude.ai connector settings, the workflow calls them as native tools — no direct CONNECT to the target domain from this environment. Jina Reader's free tier handles ~200 pages/day with no auth required; Firecrawl adds JS rendering, PDF support, and structured extraction.

The caveat: this still requires an MCP-registered endpoint that the claude.ai connector infrastructure can reach. If the connector infrastructure has similar egress restrictions, this hits the same wall. Needs testing. If it works, this is the lowest-maintenance option — no servers to run.

Services
Jina Reader (free), Firecrawl (API key, $20/mo), ScrapingBee, Browserless
Setup effort
~30 min: obtain API key, write MCP manifest, register connector.
Risk
May hit same egress restriction if MCP calls go through the same proxy. Requires validation before relying on it.
PDF support
Firecrawl: yes. Jina Reader: partial (text PDFs only, no OCR).
Modified pipeline — identical to Option A if connector works
Search → URL list → mcp__jina__read_url ×N (parallel) → Claim extraction → Verify → Synthesize
Option D Google Drive as Curated Research Corpus
Drive MCP
User curates PDFs/pages to Drive; workflow reads from there
Uses existing connected infrastructure — no new setup required
Practical near-term

Google Drive MCP is already connected and working in this environment. The workflow can read files from Drive using mcp__Google_Drive__read_file_content and mcp__Google_Drive__search_files. The split: you download key research PDFs and save them to a dedicated Drive folder; the workflow reads from that folder instead of fetching live URLs.

This is not fully autonomous for the fetch step — it requires user curation of the Drive folder. But for high-value primary sources (Stanford HAI PDF, Anthropic research papers, key industry reports) that you would read anyway, this creates a durable research corpus that improves over time. The workflow becomes: if source in Drive corpus → read from Drive; else → use snippet only. Practical immediately, zero new infrastructure.

Infrastructure
Google Drive — already connected. No new setup.
Autonomy
Semi-autonomous — fetch step requires user action (download to Drive). Processing fully automated once files are there.
Best use
Primary source PDFs you read anyway (annual reports, key papers). Not suited for broad web scraping.
Compound value
Corpus accumulates over time. Future research sessions reuse existing corpus without re-downloading.
Modified pipeline
Search → URL list → Drive lookup: in corpus? (Drive MCP) → Read from Drive if yes / snippet fallback if no → Claim extraction → Verify → Synthesize
Option E Snippet-First Hybrid with On-Demand Escalation
Hybrid mode
Run full synthesis on snippets; flag high-value sources for escalation
Pragmatic middle ground — useful output now, deeper verification when it matters
Interim mode

Accept that snippets are the primary source, but build explicit confidence tiers into the workflow output. Claims sourced from snippets are tagged SNIPPET and carry a lower confidence score. Claims from locally-available full text (Drive corpus, repo files, manually pasted content) are tagged VERIFIED and carry full adversarial verification.

The synthesis output explicitly surfaces which statistics need escalation before use in client-facing work, and from which specific sources. This makes the quality gap legible rather than hidden. Combined with Option B or D for progressive corpus building, it becomes the operating mode: most research runs in snippet mode, high-stakes claims get escalated to full fetch before use.

Infrastructure
No new infrastructure — modifies workflow logic only.
Autonomy
Fully autonomous. Output quality varies by source availability, but is always explicit about its own confidence level.
Best use
Interim operating mode while Option A or B is being built. Also a permanent complement to any fetch layer — not all claims need full verification.
Modified pipeline
Search → snippets + URLs → Classify: full text available? (Drive/repo check) → Extract from full text OR tag as SNIPPET → Adversarial verify (full text claims only) → Synthesize with explicit confidence tiers → Escalation list: sources worth fetching for depth

Recommendation Build B now, migrate to A when the research system scales

Option B (GitHub Actions) is the right immediate move. It requires the least new infrastructure, uses what you already have (this repo, the GitHub MCP tools already available in workflows), and delivers full autonomy and PDF support within about an hour of setup. The workflow triggers an action, polls for completion, reads the committed corpus — all without user intervention. The ~60 second action startup overhead is negligible for a background research process.

Pair it with Option D (Drive corpus) for primary sources you curate manually — the Stanford HAI report you already fetched is a good first entry. The workflow checks the Drive corpus first before triggering an action fetch.

Option A becomes the right architecture once the research system is being used regularly and you want a dedicated, low-latency fetch layer with caching, rate limiting, and JS rendering for dynamic pages. It's a small service that could live on Fly.io or a $5 VPS — worth building when the workflow is running weekly or more.

Option E (snippet hybrid) should be built regardless — explicit confidence tiers on all research output is good practice whether or not the fetch layer is working. It makes the quality boundary legible to anyone reading the synthesis.
