Why Gen AI, not classical ML
Gen AI vs. classical ML

Classical ML asks: what is the model predicting? Gen AI asks: what should the model generate, in what format, under what constraints? Different question, different architecture, different eval discipline. The research agenda is anchored in the second question.

The product builder vs. model builder distinction

Pre-training, instruction-tuning, RLHF — these are model builder concerns. A product team building on top of foundation models works on context architecture, RAG design, prompt iteration, structured output, and eval design. The frameworks here reflect the product builder's actual workbench.

01
Foundation — start here
Dataset Engineering for Gen AI Products
For a product team, data work means RAG corpus design and curation, few-shot prompt example selection, and eval set construction. The data strategy sets the product's capability ceiling — not the model. Data types relevant at this level: retrieval context (RAG), few-shot examples, and preference labels for fine-tuning. Pre-training data is out of scope for a product builder.
02
Amplification
Synthetic Data Generation & Self-Play Fine-Tuning (SPIN)
Bootstrap large training sets from small, high-quality seed datasets. SPIN (Self-Play Fine-Tuning, Chen et al. 2024) uses model-to-model critique — the LLM generates responses, then plays discriminator against its own outputs to iteratively improve quality. Constitutional AI applies a similar loop using written principles. Key risk: synthetic data amplifies whatever biases exist in the seed. Volume without filtering is counterproductive.
03
Calibration
Model-to-Model Critique & Multi-Agent Review
A model judging another model's output produces better calibration than single-pass generation. The underlying principle — a model judging another's output produces better calibration than single-pass generation — is applied as LLM-as-Judge (evaluation at scale), critic agents in RLHF pipelines, and multi-agent adversarial review workflows. The key design question: what makes a good judge model distinct from a good generator?
04
Orchestration
Agent Architecture & Orchestration Patterns
Multi-step autonomous systems: intent classification → capability routing → tool execution → output review → iterate. Two orchestration models: hierarchical (orchestrator + specialist sub-agents) vs. peer agent networks. CoWork, Chrome, Drive, and GitHub integrations are applied experiments in this space.
05
Memory
Context Window & Memory Architecture
The context window is not a length problem — it is a memory and retrieval architecture problem. Three memory layers: in-context (what the agent sees right now), retrieval / RAG (what it can look up), internalised / weights (what it knows from training). Context rot degrades long-horizon agent tasks as earlier information is pushed out of the active window. Managing what stays in-context, what gets retrieved, and what is dropped is an active design problem in any serious agent system.
06
Measurement — prerequisite for everything
Gen AI Evaluation Design
Evals for Gen AI are rubric-based judgments of open-ended output — not accuracy metrics. Three eval types: automatic metrics (fast, cheap, noisy), human preference labelling (slow, expensive, accurate), and model-as-judge (scalable but requires calibration). Evals must be designed before building begins, not after. An eval suite is the iteration engine — without it, there is no principled basis for knowing whether a change improved or degraded the product.

00
Optional · Context Phase
Consult — Understanding What Is Possible
Enter this phase when the solution space is unclear — you do not yet know what you do not know. The objective is to map the landscape: what tools exist, what approaches have been attempted, what constraints apply, what is realistically achievable. This is research, not specification. Skip this phase when the problem and solution are already well understood.
01
Phase 1 · Specification
Think — Landing the Concept into a Buildable Solution
Translate a high-level idea into a concrete, buildable specification — architecture decisions, component breakdown, tool selection, scope definition, and the definition of what success looks like. This phase ends when you can describe what you are about to build clearly enough that someone else could build it.
02
Phase 2 · Largest Effort
Write — Building the Solution
The solution is built: code, prompts, pipelines, RAG systems, integrations, data structures. The engineer defines what is being built; Claude Code executes the implementation. This is agentic coding in practice. The Write phase is a tight loop of specification, implementation, and local testing before the product is ready to deploy.
03
Phase 3 · Deployment
Run — Deploying to the Target Environment
The solution is deployed to its intended environment: a cloud platform, a Streamlit application, a locally hosted service, or a team-accessible tool. This phase ends when the product is accessible to its intended users and operating stably.
04
Phase 4 · Quality Gate
Evaluate — Testing Against the Eval Set
The deployed product is tested against the eval set defined in Think. If the product passes: the cycle is complete. If it fails: the failure analysis identifies which cases failed and why, and the cycle returns to Write with a targeted specification. The eval set is a living document — it grows with each iteration cycle, capturing newly discovered failure modes.

The eval set is not an afterthought. It should be drafted during Think, before a line of code is written. The eval criteria define what "done" means. A product without an eval set has no principled stopping condition and no basis for measuring improvement between iterations.

Competence Model
Four pillars of AI product competence
Four interdependent areas that together constitute the capability required to build, deploy, and improve Gen AI products. Weakness in any one area limits the others.

Interdependence: Use cases without verification procedures are liabilities. IP without a contribution model does not compound. Culture without visible success does not spread. Measurement without a defined task produces noise. The pillars are not additive — they are multiplicative.
